# AI Project Hunter

## Business Requirements Document, System Architecture & Coding Standards

**Version:** 1.0
**Date:** 12 August 2026
**Status:** Development Specification
**Product Type:** AI-powered project discovery and opportunity intelligence platform

---

# 1. Executive Summary

[Certain] AI Project Hunter is a software platform that continuously discovers publicly available software and AI project opportunities from online sources, extracts and structures project requirements, evaluates project and client quality, matches opportunities against a user's skills and preferences, ranks opportunities, generates personalized application proposals, and tracks application outcomes.

The system is initially intended for a single user and will later be extensible into a multi-user SaaS platform.

The primary objective is not simply to collect project listings.

The objective is:

> **Find projects that the user has a realistic probability of winning and that are financially worth pursuing.**

---

# 2. Business Problem

## 2.1 Current Problem

[Certain] Freelancers and independent developers spend significant time:

* Searching multiple websites for projects
* Reading long project descriptions
* Identifying required technologies
* Comparing project budgets
* Checking whether clients appear legitimate
* Determining whether a project matches their capabilities
* Writing customized proposals
* Tracking applications
* Following up with clients
* Learning which types of projects actually convert into revenue

This creates a large amount of repetitive work.

## 2.2 Business Opportunity

[Likely] An intelligent system can automate much of the discovery and analysis process while keeping the final client interaction under human control.

The platform should answer:

> "Which projects available right now are worth my time?"

rather than:

> "What projects are available?"

---

# 3. Product Vision

## Vision

Build an AI-powered opportunity intelligence system that becomes a personal project-hunting agent.

The long-term system should understand:

* What the user can build
* What the user has previously built
* What projects the user prefers
* Which clients are trustworthy
* Which projects are financially attractive
* Which projects the user is likely to win
* Which proposals produce responses
* Which project categories generate revenue

---

# 4. Product Objectives

## Primary Objectives

[Certain]

1. Discover project opportunities automatically.
2. Normalize project information from different sources.
3. Extract structured requirements using AI.
4. Detect duplicate opportunities.
5. Match projects against the user's skills.
6. Score opportunities using explainable criteria.
7. Analyze available client-quality signals.
8. Rank opportunities by expected value.
9. Generate personalized proposals.
10. Track applications and outcomes.
11. Learn from historical results.

## Secondary Objectives

1. Reduce time spent searching.
2. Increase quality of applications.
3. Increase application response rate.
4. Increase project conversion rate.
5. Improve project selection over time.
6. Eventually support multiple users.

---

# 5. Non-Goals for MVP

[Certain] The following should NOT be implemented in Version 1:

* Fully autonomous client communication
* Automatic proposal submission
* Automatic bidding
* Payment processing
* Mobile application
* Microservice architecture
* Kubernetes deployment
* Complex autonomous multi-agent architecture
* Training a large custom language model
* Ten or more data sources
* Real-time browser automation for every platform

These may be considered after the core system is validated.

# 11. Duplicate Detection

## FR-005: Duplicate Identification

The system shall identify potentially duplicated projects.

Detection should combine:

* Source project ID
* URL
* Title similarity
* Description similarity
* Client similarity
* Embedding similarity

The system should preserve the original records while linking them as duplicates.

# 15. Client Analysis

## FR-009: Client Quality

Where publicly available, the system should evaluate:

* Previous project history
* Reviews
* Hiring history
* Account/profile information
* Public company information
* Domain information
* Project consistency
* Suspicious requirements
* Unrealistic budgets
* Potential scam indicators

The system should never claim that a client is definitely fraudulent unless there is reliable evidence.

Output:

```text
Client Score: 82/100

Positive Signals:
- Previous hiring history
- Relevant project history

Warnings:
- Budget appears unusually low
```

# 23. Architecture Principles

## Principle 1: Modular Monolith First

[Certain] Keep one deployable backend while maintaining strict internal modules.

* Easier development
* Easier debugging
* Easier deployment

* Lower infrastructure cost

# 26. Collector Architecture

[Certain] Every source should implement a common interface.

Conceptually:

```text
BaseCollector
│
├── SourceCollectorA
├── SourceCollectorB
├── SourceCollectorC
└── SourceCollectorD
```

The rest of the application should not care where a project came from.

The collector should return a normalized internal object.

```text
External Source
      ↓
Collector
      ↓
Raw Project
      ↓
Normalizer
      ↓
Canonical Project
```


# 30. Processing Pipeline

[Certain] Every project should pass through a predictable state machine.

```text
COLLECTED
    ↓
NORMALIZED
    ↓
VALIDATED
    ↓
DUPLICATE_CHECKED
    ↓
AI_EXTRACTED
    ↓
SKILLS_MATCHED
    ↓
CLIENT_ANALYZED
    ↓
SCORED
    ↓
RANKED
    ↓
PRESENTED
```

Failed processing should not destroy the original project.

Example:

```text
AI_EXTRACTION_FAILED
```

The project remains available for retry.

# 33. Coding Standards

## Rule 1: Type Everything

Use Python type hints.

```python
def calculate_score(
    skill_match: float,
    budget_score: float,
) -> float:
    ...
```

## Rule 2: Small Functions

Avoid:

```text
process_everything()
```

Prefer:

```text
collect()
normalize()
validate()
extract()
score()
persist()
```

## Rule 3: No Business Logic in API Routes

Bad:

```text
router
 └── 300 lines of business logic
```

Good:

```text
router
  ↓
service
  ↓
domain
  ↓
repository
```

## Rule 4: No Hardcoded Secrets

Never:

```python
API_KEY = "..."
```

Use environment variables.

## Rule 5: Validate External Data

Never trust data received from:

* APIs
* Websites
* Users
* LLMs

LLM output is also external input.

# 37. AI Safety and Reliability Rules

The AI must not:

* Invent user experience
* Invent portfolio projects
* Invent client information
* Invent budgets
* Invent deadlines
* Claim uncertain information as fact

Every extracted field should have a confidence or evidence source where practical.

Example:

```json
{
  "budget": {
    "value": 120000,
    "currency": "INR",
    "source": "project_description"
  }
}
```

# 50. First Implementation Milestone

Do **not** start by implementing the entire architecture.

Your first milestone is deliberately small:

```text
Git Repository
      ↓
Python Project
      ↓
FastAPI
      ↓
PostgreSQL
      ↓
One Project Collector
      ↓
Normalized Project Model
      ↓
Store 50+ Projects
      ↓
Unit Tests
```

Only after this works should the AI layer be introduced.

The development order is therefore:

**Foundation → Data → AI → Matching → Scoring → API → UI → Proposals → Automation → Learning.**

That ordering gives you a proper engineering education while simultaneously producing a usable product. By the time the project is finished, you should be able to delete the AI-generated scaffolding, recreate the architecture yourself, and explain why every major component exists. That is the standard worth aiming for.
